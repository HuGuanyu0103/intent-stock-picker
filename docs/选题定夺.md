# 选题定夺：02自然语言选股 vs 08事件情报时间线

> 结论先行：**推荐选题 02（自然语言智能选股与策略解释器）**。它在 24 小时约束下的落地确定性、与给定数据源的匹配度、与你已有资产的复用率三个维度都明显占优；选题 08 天花板更高、赛道更空白，但核心难点（跨源事件合并、版本状态机）恰是工业界尚未解决好的问题，24 小时内做出"可信主链路"的风险大，更适合作为赛后一周期项目。

## 一、两道题的本质差异

| 维度 | 02 自然语言选股 | 08 事件情报时间线 |
|---|---|---|
| 核心任务 | 模糊意图 → 可检查可修改的结构化条件 → 确定性筛选 → 入选/排除解释 | 多源资讯 → 事件识别/合并/跟踪 → 事实观点传闻分级 → 更新否认更正驱动结论变化 |
| AI 的理想位置 | 意图翻译层（Schema 约束输出） | 抽取、相似度判断、合并裁决、摘要 |
| 确定性部分 | 筛选引擎（字段比较、聚合、过滤） | 状态机、时间字段管理、证据权重计算 |
| 最难的技术点 | 模糊词映射口径、条件冲突检测 | **事件共指消解（误合并/漏合并）**、跨源版本对齐 |
| 输出可验证性 | 强：每条结论可回到字段值 | 弱：合并对错依赖人工判断，需构造评测集 |
| 演示数据依赖 | 当日真实行情即可，任何交易日都能演 | 需要一条"传闻→否认/证实→更新"的完整事件链，靠运气或提前回放 |

02 的难是"产品设计难"（口径、交互、解释），工程量可控；08 的难是"算法效果难"，LLM 单次抽取便宜，但**把多篇报道正确聚成同一个事件并维护其生命周期**，是学术前沿问题——时间线摘要（TLS）的主流流程至今仍是"事件检测→聚类→摘要→时间线"四阶段流水线，2025–2026 年的最新论文仍在用轻量 LLM + 粗/细两阶段混合聚类来降低误合并（[Springer 2026, ICAUS](https://link.springer.com/chapter/10.1007/978-981-95-7656-2_10)）。中文金融文档级事件抽取的权威数据集 ChFinAnn、DuEE-Fin 也只覆盖单文档内多事件，不含跨源合并与版本管理（[知乎综述](https://zhuanlan.zhihu.com/p/626510681)）。这意味着 08 没有现成轮子，24 小时内合并质量一旦不稳，演示现场最显眼的就是"把两件事混成一件"。

## 二、开源生态调研

### 选题 02 方向：工具链成熟，竞品多为"黑箱选股"而非"可审计选股"

- **Vanna**（约 2.38 万星）：RAG 式 text-to-SQL 事实标准，MIT 协议，2026 年已归档（read-only），但 RAG 方案本身成熟可借鉴（[DEV 综述 2025](https://dev.to/veilanalytics/best-open-source-text-to-sql-tools-in-2025-ranked-by-privacy-performance-5emg)）。同类还有 WrenAI（约 1.2 万星）、SQLCoder。
- **AI 量化/选股类项目极度拥挤**：Qlib 约 4.2 万星、ai-hedge-fund 约 5.4 万星、daily_stock_analysis 约 6.55 万星（2026 年 1 月建仓，5 个月冲到近 4 万，[GitHub 仓库页](https://github.com/ZhuLinsen/daily_stock_analysis)；[2026 年 6 月盘点](https://gamesite.top/posts/2026-06-26-ai-quant-github.html)）、go-stock 7.6 千星、tick-stock-panel 4.9 千星。
- **关键观察**：这些项目几乎都是"喂数据→LLM 出报告/评分"，没有一个把重点放在**意图澄清对话、条件 JSON 可编辑、冲突提示、逐只股票的入选/排除字段级解释、条件敏感性对比**上。拥挤的是"AI 荐股分析"，空白的是"AI 做翻译、引擎做判断、全程可审计"。

### 选题 08 方向：没有可直接复用的成品，学术工具与题目要求错位

- **FinNLP**（AI4Finance，约 1.5 千星）定位是资讯**采集器**（新浪、东财、Finnhub 等源的下载管线），不含事件合并与时间线（[GitHub](https://github.com/ai4finance-foundation/finnlp)）；FinGPT（约 2.13 万星）提供情绪分析能力，同样不做事件生命周期管理（[GitHub](https://github.com/AI4Finance-Foundation/FinGPT)）。
- 事件抽取侧只有数据集与论文方案（Doc2EDAG/ChFinAnn、DuEE-fin），无开箱即用服务；时间线摘要侧是研究原型不是产品。
- **结论**：08 方向更空白、更新颖，但所有"脏活"（采集去噪、实体归一、合并、状态机、评测集）都要在 24 小时内自建。

## 三、商业产品格局

**02 方向有一个碾压级在位者，必须正面回答"你和问财有什么不同"：**

- 同花顺 **i问财** 是财经领域落地最成功的自然语言选股系统，支持百万级指标、自然语言组合条件、问句保存迭代、回测，甚至开放了 `query_iwencai` 量化接口（[同花顺 SuperMind 文档](https://quant.10jqka.com.cn/view/dataplatform/detail/398)）。东方财富妙想、华泰 AI 涨乐也都有 NL 选股入口。
- 但问财类产品的结构性短板恰好是题目 02 的得分点：**条件是黑箱翻译（用户看不到、改不了结构化口径）、只告诉你谁入选、不告诉你谁被排除以及卡在哪个字段、条件改动影响不可见**。第三方实测也把问财定位为"把条件翻译成数据库查询的筛子"（[实测文章](http://m.toutiao.com/group/7670945633158627884/)）。
- 08 方向的商业存在：问财"事件预测/投资事理图谱"、华泰"事件捕手"、财联社题材库，但都偏"事件→影响解读"，**同样没有人认真做"多源版本合并 + 事实/观点/传闻分级 + 否认更正翻转结论 + 四时间戳"**。08 的产品空白比 02 大，这是它的上限优势。

## 四、给定数据源的匹配度（实测）

- **扶摇**：行情快照、历史 K 线、指数/板块成分、估值、三大财务报表多期序列、交易日历、涨跌停热榜全部可用，REST 与 MCP 同鉴权（[扶摇文档](https://fuyao.aicubes.cn/docs/)）。这正是 02 的筛选引擎所需的全套字段。
- 扶摇虽有"资讯事件库"接口（事件标题、摘要、标准时间、A–E 评级、关联行业概念），但文档明确标注**"暂未开放外部接入，仅同花顺 AI 客户端内使用"**，且不开放事件主体、关联个股、新闻来源字段，也没有版本/否认/更正状态（[资讯事件库文档](https://fuyao.aicubes.cn/docs/api-reference/news-events/)）。也就是说：08 最想要的"合并好的事件"数据**用不了**，能依赖的只有 iFinD MCP 的新闻接口（题目声明含"政策、新闻"数据，但工具粒度与字段未在文档公开，存在不确定性）。
- 匹配结论：02 = 数据源与题目严丝合缝；08 = 核心数据依赖单一未验证通道，且需要自己解决同一事件的多稿对齐。

## 五、与你已有资产的复用与互补

| 已有资产 | 对 02 的复用 | 对 08 的复用 |
|---|---|---|
| 观澜 layer2_scan（9 形态/19 因子/screener） | 直接改造成"结构化条件→确定性筛选引擎"，过滤链、归一化、百分位口径现成 | 基本用不上 |
| layer3_backtest 回测 | 题目要求"可转回测"，直接接 | 无关 |
| guardrails/compliance_eval/agent_eval | 合规红线、离线评测体系直接迁移 | 评测框架可迁移，内容重建 |
| Structured Output Agent + 6 条自检 | 意图澄清、条件 JSON 约束输出同构 | 抽取/合并 prompt 可参考 |
| news_monitor.py（财联社采集+规则+LLM） | 无关 | 仅采集层少量复用 |
| stock-daily-digest 的"LLM 只做翻译、判断归规则与人、证据可溯源、人在回路" | **设计语言完全一致**，PRD 与评测方案的思维框架可直接沿用 | 证据分级、时间戳披露可沿用 |

作品集叙事上，02 还能和你两个项目串成一条完整的投前/投中/投后产品线：**02 投前选股（意图→条件→候选）→ 观澜投中决策陪练 → 当日解读投后归因**，三者共用同一条"AI 不越界"的产品主张，面试时是一个体系而不是三个散点。08 则是旁支出一条全新的资讯情报线。

## 七、推荐 02 的打法：不打指标广度，打"可审计"

1. **一句话定位**："问财告诉你结果，我告诉你机器为什么这样理解你、每只股票为什么进/为什么没进。"核心演示路径：输入"经营改善、估值合理、走势相对稳定" → AI 反问澄清 1–2 个模糊点 → 生成三块可编辑条件卡（每条标注：字段、口径、报告期、AI 理解置信度）→ 检测出条件冲突（如"低估值"+"高增速赛道"）并提示 → 候选列表每只展开**入选证据（命中字段实际值）**，并排展示**只差一个条件的"差一点"股票及卡点字段** → 拖动/修改任一条件，结果集与入选数量实时变化。
2. **架构直接沿用你的招牌分层**：LLM 仅产出受 Schema 约束的条件 JSON + 澄清问句；冲突检测、筛选、口径计算全部确定性执行；数据缺失/接口失败显式降级，不静默出结果；合规层拦截荐股措辞。这与你简历里"LLM 不能直接分析裸数据"的主张完全互证。
3. **24h 排兵布阵建议**：第 0–3h 搭扶摇数据适配 + 条件 Schema；3–9h 筛选引擎（复用观澜 screener 思路，因子收窄到 15–20 个高频口径）+ 排除原因归因；9–14h 意图澄清/冲突检测 LLM 链路；14–19h 前端（对话→条件卡→结果+证据→条件对比）；19–22h 三类必测场景（主链路、接口失败/字段缺失、合规边界）+ AI 使用记录；22–24h 录屏与 README。
4. **主要风险与化解**：① 被问"和问财比"——回答框架是"问财是黑箱查询，我是可检查可修改可追溯的条件协作台，目标是让用户学会并掌控自己的选股标准"；② 模糊意图映射错——用"先澄清后执行 + 置信度低的条件标黄待确认"把错误变成产品特性；③ 指标覆盖少——明确写进"已知边界"，不与商业终端比广度。

## 八、什么情况下应改选 08

- 你能提前确认 iFinD MCP 新闻接口返回**标题+正文+来源+时间戳**且可按个股/关键词拉取历史新闻（建议动手前先用 30 分钟实测一个工具调用，这是 08 的生死检查点）；
- 你愿意把目标收敛为：**单只重点标的、单一事件类型（如并购/减持/业绩预告）、预置 1–2 条真实历史事件回放数据**，用"确定性规则优先 + LLM 兜底合并 + 人工确认合并"的保守策略，不追求全自动；
- 你更想要一个高风险高回报、赛后可持续做一周的项目，而非 24h 稳交付。

若以上三点都满足，08 的"传闻→多家报道→公司否认→正式公告"翻转时间线演示会非常出彩，且与你当日解读项目的证据链设计呼应。但在当前信息下，它的交付确定性显著低于 02。
