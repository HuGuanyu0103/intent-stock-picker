# 评测体系：MVP 成立标准、评测方法与迭代动作映射

> 适用对象：条件协作台（自然语言智能选股与策略解释器）。
> 设计原则三条：① 金融产品的评测红线先于体验指标；② 离线门禁保"不犯错"，在线行为看"有没有用"；③ 每个指标都必须能映射到一个具体迭代动作，不做只看不动的 vanity metric。

## 一、产品假设与 MVP 成立的定义

### 1.1 核心假设链（H1→H4，MVP 要逐一证伪/证实）

- **H1 翻译可信**：AI 把模糊意图翻译成结构化条件的准确率足够高，用户敢在条件卡上点"执行"。
- **H2 可审计创造信任**：逐条件证据 + 差一点/不可判定分组，比黑箱列表更能让用户理解并信任结果（即使结果与他预期不同）。
- **H3 条件可改性有用**：专家值三档与试算计数让用户愿意且能够把条件调成"自己的标准"，而不是盲信或放弃。
- **H4 增量收窄形成闭环**：用户会用追加条件/改阈值做二次筛选，完成一次完整的"提问→检查→执行→修正"研究动作。

### 1.2 MVP 成立标准（三层，全部满足才算"成立"）

**红线层（一票否决，不设阈值容忍）**

| 指标 | 成立线 |
|---|---|
| 合规违规（涨跌预测/买卖建议/收益承诺） | 0 例（离线诱导集 + 在线） |
| AI 编造白名单外指标 | 0 例（Schema 架构保证） |
| 文案数字与引擎结果不一致（幻觉） | 0 例（架构保证：数字只来自结果对象） |
| 数据缺失被静默当正常结论输出 | 0 例（unknown 必须落隔离组） |

**能力层（离线评测集，发布门禁）**

| 指标 | MVP 成立线 | 优秀线 |
|---|---|---|
| 意图接地准确率（条件 JSON vs 人工标注，字段级完全匹配） | ≥85% | ≥92% |
| 澄清/挂起触发精确率 | ≥80% | ≥90% |
| 应挂起表达的召回率（未理解 + 口误） | ≥85% | ≥95% |
| 引擎三值判定与人工复核一致率 | 100%（确定性代码，靠单测锁） | 100% |
| 异常场景（超时/Key 缺失/未披露/空结果）正确处理率 | 100% | 100% |

**效用层（5–10 人可用性测试 + 上线行为，demo 期样本小但必须跑）**

| 指标 | MVP 成立线 |
|---|---|
| 黄金路径独立完成率（无提示走通：输入→执行→说出一只股票为何入选） | ≥80% |
| 结果可解释感知（任务后问卷"你能说清为什么是这些股票吗"） | ≥4/5 |
| 信任校准（结果反直觉时，仍认可"过程合理"的比例） | ≥70% |
| 条件编辑率（至少改过一次阈值/档位的会话占比） | 落在 30%–70% 甜区 |
| 二次筛选使用率（追加条件或重跑 diff） | ≥30% |
| NPS / 愿用意愿 | ≥4/5 |

**编辑率为什么是"甜区"而不是越高越好**：接近 0 = 用户在盲信（产品没让他真正参与）或看不懂卡片；接近 100% = 专家值不被认可（默认口径失败）。30%–70% 说明默认值可用、但用户确实在行使控制权——这正是"协作台"要的状态。

## 二、评测体系：三层结构

### 2.1 离线评测（每次发版前的门禁，可自动化）

**A. 意图解析评测集（目标 30–50 条，MVP 先 20 条）**

每条含：原始表达、期望 polarity/metric/op 形态、期望触发（成卡/澄清/挂起/拦截）。分层构造：

1. 标准三类短语（经营改善/估值合理/走势稳定）的多种说法（5 条）；
2. 排除表达：显性否定、隐性否定（"没有退市风险的"）、集合排除（"除了银行"）、多红线同句（4 条）；
3. 口误与矛盾（"低估值的不要"）（3 条）；
4. 不可量化表达（"龙头""股性活""有想象空间"）（3 条）；
5. 合规诱导（"明天涨停的""推荐几只"）（5 条，红线集只增不减）；
6. 噪声（闲聊、纯个股代码、空输入、超长文本）（3 条）。

评测维度与统计：接地字段级准确率、极性识别准确率（include/exclude）、澄清/挂起精确率与召回率、红线拦截率（必须 100%）。产物：`tests/eval_intent.jsonl` + 跑分脚本，进入提交的"AI 使用与验证记录"。

**B. 引擎正确性评测（已有 17 项单测，持续扩充）**

- 三值逻辑：pass/fail/unknown 边界（null、负值、零、布尔）；
- 四分组归属：全 pass/单条 fail/多条 fail/触发排除/排除项 unknown；
- 硬冲突：区间有交集/无交集/不同指标互不误报；
- diff：新增、掉出、不变；
- 试算计数与引擎实际分组数的一致性（对账测试：卡片计数 = 真实分组聚合）。

**C. 数据一致性抽检（每个预热批次）**

- 随机抽 10 只股票，人工对照扶摇原始字段核对指标计算（PE 分位、波动率、回撤、同比）；
- 检查 unknown 比例异常漂移（如某日财务接口全挂会导致 unknown_data 飙到 ~100%，要有批次级告警阈值）。

### 2.2 在线行为指标（埋点驱动，定义见第三节）

冷启动现实：黑客松后真实流量极少，因此在线指标分两阶段——
- **阶段一（赛期，5–10 人定向可用性测试）**：用埋点回放 + 现场观察 + 任务后问卷，样本小但要逐会话看；
- **阶段二（真实流量后）**：看聚合趋势与漏斗，按周复盘。

### 2.3 专家评审/人工质评（每周或每版）

固定 3–5 个"金标准 query"（就是演示那三个），每版手工完整走一遍并截图存档，防止版本迭代让黄金路径退化（回归演示集）。

## 三、埋点方案（MVP 最小集，约 10 个事件）

后端 `POST /api/events` 落 JSONL（本地文件，无第三方、无用户身份），前端在以下时点上报：

| 事件 | 关键属性 | 回答的问题 |
|---|---|---|
| `session_start` | 入口（示例/手输） | 流量从哪来 |
| `intent_submit` | 文本长度、是否示例 | — |
| `conditions_built` | 条件数、include/exclude 数、挂起数、耗时 | H1 翻译成功率 |
| `condition_edit` | condition_id、字段（阈值/档位/删除）、改前改后 | H3 编辑率、哪条专家值不被认可 |
| `trial_view` | （停留时长代理：运行前停留秒数） | 试算计数有没有被看 |
| `screen_run` | 条件指纹 hash、入选/差一点/排除/不可判定数 | 条件组合分布、空结果率 |
| `evidence_expand` | thscode、所在页签 | H2 证据是否被消费、差一点页签吸引力 |
| `tab_switch` | from→to | 各分组关注度 |
| `refine_submit` | 追加文本、新增/掉出数 | H4 闭环使用率 |
| `scheme_save` | 条件数 | 保存需求强度 |
| `compliance_block` | 触发词 | 红线分布 |

派生的核心漏斗：`提交 → 成功生成条件 → 运行 → 展开过任一证据 → 编辑/追加/保存`。

**两个关键的"反虚荣"口径**：
- "运行次数"不是成功指标——反复运行却从不展开证据，说明用户在当黑箱摇奖；
- 入选股票数不是成功指标——条件过松导致几百只入选等于产品失败，要监控"空结果率"和"超量率（>50 只）"双向异常。

## 四、数据看板与复盘节奏（轻量）

赛期用一个 notebook / 脚本每天出一张表，四行足够：

1. **漏斗**：各步转化率，哪一步漏人；
2. **条件画像**：最常被改的 Top 3 条件、各档分布、空结果/超量结果占比；
3. **分组消费**：四页签的展开率、差一点→回看条件的比例；
4. **质量**：unknown 比例、合规拦截数、前端异常数。

## 五、指标 → 诊断 → 迭代动作映射表（评测的最终目的）

| 观测到的信号 | 可能原因 | 迭代动作 |
|---|---|---|
| 接地准确率低，集中在某类短语 | 词典缺义项/阈值口径错 | 扩同义词、拆子义项；新增 case 进离线集锁回归 |
| 澄清/挂起精确率低（用户觉得"这有啥好问的"） | 过度保守，常识短语被挂起 | 给该义项补专家默认值，降为直译成卡+低置信标记 |
| 挂起召回低（用户输入了系统不懂的却被硬配） | 白名单太宽/匹配太松 | 收紧关键词、加"必须同时命中两词"规则 |
| 条件编辑率 <30% | 盲信或没看懂卡片 | 强化口径一句话理由、首次引导展开试算计数、卡片加"为什么是这个值" |
| 条件编辑率 >70%，集中在某条 | 该专家值口径不被认可 | 重设三档阈值/改默认档（如波动率 40% 太严） |
| 空结果率高（入选 0） | 条件默认过严/缺软权衡提示 | 强化运行前交集预估与"预计命中 0–3"提示；提供一键放宽 |
| 超量率高（入选 >50） | 默认过松 | 调严中档；上线 P1 的"AI 收紧建议" |
| 差一点页签展开率高 | 排除解释正中痛点 | 做"差一点→一键放宽该条件到刚好入选"；把卡点字段做成可点改的快捷入口 |
| 证据展开率低 | 用户不信任/没注意可展开 | 首只默认展开、证据摘要前置到列表行 |
| 追加条件使用率低 | 入口不显眼/不会写 | 给快捷追加 chip（"成交额更大""只要龙头行业"）、把 facet 行业过滤做出来 |
| unknown_data 比例突增 | 上游接口故障/财报季口径切换 | 批次告警、预热重试、状态条明示数据源降级 |
| 合规拦截出现漏网 | 红线词表不全 | 新词进 50 条诱导集，回归门禁，永远 0 容忍 |
| 用户反复运行同一条件多次 | 结果不稳定或在试阈值 | 固化结果缓存；阈值拖动即给预估数，减少盲跑 |
| 信任问卷分低但接地准确率高 | 问题在"被理解感"而非正确性 | 优化解读流叙事、原话-卡片高亮联动，让用户先感到被听懂 |

## 六、版本迭代路线（评测结论如何排优先级）

- **v1.0（当前黑客松版）**：规则解析 + 8 指标 + 四分组 + diff + 保存；证明 H1–H4 的主链路成立。
- **v1.1（评测驱动）**：按离线集错误修词典；行业/概念集合条件（消灭最高频的"未理解"）；试算→一键放宽。
- **v1.2（效用深化）**：轻量回测（题目 P1）、方案监控（diff 定时化）、比较视图。
- **v1.3（AI 升级，有数据后才做）**：规则覆盖不足的长尾表达接 LLM 解析（输出仍受同一 Schema 与白名单约束），用线上"接地失败→人工标注"样本做 few-shot；**是否值得上 LLM 由数据决定**：若规则版接地率已 ≥92%，上 LLM 的边际收益不抵稳定性损失，就不上——这个决策本身写进 AI 使用记录。

## 七、给评审的一句话评测叙事（可直接用于答辩）

"这个产品的评测不靠选股收益——24 小时也无法证明收益。我把'AI 产品是否成立'拆成可证伪的三层：红线 0 容忍且由架构保证、翻译准确率与判定正确性由离线门禁量化、协作效用由用户编辑率和证据消费率验证；每一个指标异常都预先写好了对应的产品动作，评测不是交差文档，是下一个版本的需求来源。"
